# Harness assumptions

Each piece of scaffolding, the weakness it covers, and how to tell when it can go (decision 29).

| Scaffolding | Covers | Remove when |
|---|---|---|
| Live canary probe in `jarvis doctor` (decision 59) | Claude Code silently drops a whole `--settings` file when one value is invalid, so a written file isn't proof the protections are on | Claude Code fails loudly on invalid settings in `-p` mode *and* exposes the effective sandbox config in `init`. Keep the probe anyway as a smoke test. |
| Positive controls in the probe | A dropped settings file plus `dontAsk` refuses everything, which would otherwise look like "everything blocked = safe" | Never; it's what makes the probe meaningful |
| `realpath` for socket and sandbox paths | The macOS sandbox matches only real paths (`/tmp` → `/private/tmp`) | Claude Code resolves symlinks itself (re-test on each pin) |
| Built-in-plugin filter in the probe | 2.1.309 lists `…@builtin` plugins in `init` even with `--setting-sources project` | Not a weakness: keep it, re-check the format on each pin |
| Clean child environment (decision 58) | Wrappers and shell profiles can reroute or rebill a session | Never |
| ntfy answer confirmations and first-answer-wins (decision 50) | The iOS ntfy app gives no feedback after a button tap, so people tap repeatedly | The ntfy iOS app shows tap feedback; keep first-answer-wins regardless |
| The sandbox denial record required by the probe's network check | curl's `000` can't tell a policy denial from a DNS or TLS failure | Never; it's the evidence that the policy, not luck, blocked the host |
| Private per-run toolchain cache | Sessions can write the cache, so a shared one carries data between runs | A runner-managed read-only mirror plus a private overlay gives the same isolation faster |
| A short private temp folder per session (`mkdtemp /private/tmp/jt-XXXXXX`, 0700) passed as `CLAUDE_CODE_TMPDIR`, reopened with `allowRead`/`allowWrite` for exactly that path and removed afterwards (decision 93) | 2.1.309 gives sandboxed commands `TMPDIR=<CLAUDE_CODE_TMPDIR>/claude-<uid>` only when that path is at most 44 bytes (AF_UNIX socket names). Longer, and it falls back to `/tmp/claude-<uid>`, which every Claude Code session of the user shares and decision 93 makes unreadable. Observed live with a cache-folder path: TMPDIR `/tmp/claude-501`, files written there couldn't be read back, and pipes, redirects and `&&` ran but reported errors. A cache folder under `~/.jarvis-work` is too long for the limit | Claude Code accepts a long `CLAUDE_CODE_TMPDIR` for sandboxed commands, or has its own sandbox TMPDIR setting (re-test on each pin; the probe's `positive_session_tmpdir_usable` fails if TMPDIR isn't the session's folder) |
| `/usr/bin` shims (`git`, `python3`) print `couldn't create cache file '/var/folders/…/xcrun_db-…'` under decision 93 (seen with the pinned sandbox runtime library, not yet in a live session) | xcrun keeps its lookup cache in the per-user temp folder under `/var/folders`, which sessions can no longer read. The command still runs; xcrun re-runs `xcodebuild` to find the developer folder | Never needed for safety; set `DEVELOPER_DIR` if the extra lookup ever costs real time |
| `__CF_USER_TEXT_ENCODING` allowed in the review runner's environment test (decision 66) | macOS adds it to every started process, even under `env -i`; the runner supplies only four keys | Never on macOS; re-check the observed set on each macOS update, and allow nothing else |
| Avoiding compound shell commands in sessions (stage 3 build and debug skills: one plain command per call; repeated work goes in a `.jarvis/scratch/` script run with `sh`) | Under `dontAsk`, Claude Code refuses some compound commands even when sandboxed. Observed on 2.1.309 by the live probe's `shell_composition_recorded` (Oct 24, three sessions alike): a pipe (`printf … \| tee f`), a redirect (`printf … > f`) and `&&` run; a `for` loop is refused with "Permission to use Bash has been denied because Claude Code is running in don't ask mode. IMPORTANT: You *may* attempt to accomplish this action using other tools…". The workaround works: the Write tool writes `.jarvis/scratch/x` and `sh .jarvis/scratch/x` runs (`positive_scratch_script_runs`). `while`, `if`, `case`, subshells and `$(…)` weren't tried, so the skills' "one plain command" rule is stricter than needed only for pipes, redirects and `&&` | The probe shows `for` runs on a new pin (it re-tests every run; a changed answer shows in its detail) |
| The install's `packages/cli/bin/jarvis` launcher first on a task session's `PATH`, run with `JARVIS_NODE` (the runner's own Node, by real path) (`harness/claude/task.ts`) | Sessions can't read the home folder (`blockReadsOutsideWorkingDirectories`), so the `~/.local/bin/jarvis` launcher `scripts/install.sh` writes can't run there, and a session's `PATH` needn't hold Node 24. It assumes 2.1.309 gives sandboxed Bash commands the session process's `PATH`: its shell snapshots end with `export PATH=<the process's PATH>` (seen in `~/.claude/shell-snapshots`), but no live session has run `jarvis act` from `PATH` yet (the live safety test calls `node <install>/packages/cli/src/cli.ts`) | A live session's `command -v jarvis` resolves to the launcher and its `jarvis act` returns pending; re-check on each pin. Remove if sessions reach the broker some other way |
| The runner's commit walk refuses files with more than one link (`runner/worktrees.ts`), and the probe's `hardlinks_out_refused` | A hard link is a second path to the same file, and the sandbox judges paths. On 2.1.309 Seatbelt refuses `ln` into the worktree of every file the session can't write (a readable file beside the worktree, a read-denied runner-folder file, the write-denied `.git/config`: "Operation not permitted"), but a file it can write outside the worktree, its own toolchain cache, links fine | Never: defense in depth |
| `jarvis decide --by user` trusts its caller (decision 85) | Firmness holds only if a session never claims to be Fabricio; the skills record `--by user` only for answers they received from an intake round | `--by user` checks the ledger for the intake answer it cites |
| gitleaks always reads `<source>/.gitleaksignore`, whatever `--gitleaks-ignore-path` says (8.28.0, verified live) | The security pass refuses to scan when `.gitleaksignore`, `.semgrepignore`, `osv-scanner.toml` or `.osv-scanner.toml` sits at the candidate root, in any file type; semgrep runs with `--disable-nosem` | Remove when the scanners take an explicit ignore-file path that overrides the root file |
| gitleaks 8.28.0 replaces its whole ruleset with `<source>/.gitleaks.toml` when no `--config` is given; OSV 2.7.0 loads an `osv-scanner.toml` next to every scanned lockfile, at any depth (both verified live, Oct 25: a candidate file gave exit 0 and no findings) | The security pass also refuses to scan when `.gitleaks.toml` sits at the candidate root. OSV runs with `--config=/dev/null`, which replaces every per-folder config (verified live: the planted finding returns), and the adapter refuses OSV pins without it | Re-test both at every gitleaks or OSV pin change |
| gitleaks `dir` scans the working tree only, not git history, and its default config allowlists `node_modules/` | Recorded coverage gaps of the security pass; history and dependency secrets aren't checked | Revisit with a history scan of the candidate's new commits |
| The sandbox runtime refuses writes to `.gitmodules`, `.claude/commands/` and similar paths everywhere, even inside the run folder | Checks that unpack third-party archives inside the sandbox ship them pre-extracted (the Go module cache fixture) | Revisit if srt makes these protected paths configurable per run |
| Codex's own sandbox off (`--sandbox danger-full-access`) inside Jarvis's outer Seatbelt profile (decision 110) | Codex's `read-only` sandbox confines writes, not reads, and on this macOS (Darwin 25.5) a Seatbelt-confined process can't apply a second, different profile (`sandbox_apply: Operation not permitted`), so Codex's per-command sandbox would fail every command under ours | Codex can confine its own process and commands to named read roots (its permission profiles cover the Codex process too), verified by the canary tests on a new pin; or macOS allows nesting a stricter profile |
| The confined Codex reaches its API only through a runner-owned CONNECT proxy (`HTTPS_PROXY`), and verifies TLS against `/private/etc/ssl/cert.pem` (`CODEX_CA_CERTIFICATE`) (decision 110) | Seatbelt filters network by address, not hostname; Codex 0.164.0's platform TLS verifier needs securityd, which the profile keeps closed (observed: `invalid peer certificate: UnknownIssuer` without the bundle) | Re-check on each Codex pin: the live test (`JARVIS_CODEX_LIVE=1`) fails if Codex stops honoring the proxy or the bundle |
| Codex 0.164.0's npm launcher (`bin/codex.js`, `#!/usr/bin/env node`) runs on Homebrew's node, so the confined reviewer gets the node keg and the 13 library kegs it loads, found by reading Mach-O load commands (decision 110) | The profile can't open `/opt/homebrew` (its `var` and `etc` hold a Tor key and PostgreSQL data), and node won't start without its dylibs. | Semgrep runs with `--max-target-bytes=0`, and `offlineArgs` refuses a Semgrep pin without it (backlog 92) | Semgrep 1.182.0 skips every file over 1 MB by default and says nothing about it: the file is just missing from `paths.scanned`, with no `paths.skipped` entry, no error and exit 0 (verified Oct 25 on a padded `eval`; with the flag the file is scanned and the finding reported).
