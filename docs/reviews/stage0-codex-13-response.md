| # | Severity | Finding | Response |

| 1 | high | Literal HTTP authorization credentials pass the snapshot scan | **Fixed by header structure:** in every file, `Authorization` or `Proxy-Authorization` followed by a scheme (`Bearer`, `Basic`, `Token`, `Bot`, `Digest`, `ApiKey`) and a literal is a credential, whatever its length or characters (short, long and non-ASCII Basic values included). `authorization` is also a credential field in structured configs, judged by the credential after its scheme. Interpolations (`Bearer ${token}`, `"Bearer " + key`), references (`$KEY`, `${API_TOKEN}`) and documentation placeholders stay: `<token>`, an elided `fhk_…`, an HTML-escaped `&lt;key&gt;`, or lowercase words (`token`, `the-token`, `fhk_whatever`). **Known limit:** a real token made only of lowercase letters and separators passes; random tokens are mixed-case or have digits. In FreeHire this left three test files with fake values (`tok-123`, `tok-9`, `foo:bar`), now listed as reviewed in jarvis-evals. **Tests:** refusals for an opaque Bearer token in JSON and in a `.http` file, a short and a 400-character Basic value in code, a non-ASCII `Proxy-Authorization`, and a bare `authorization` field; the inert snapshot keeps interpolations, a reference, a placeholder and word-like fixtures. **Mutations:** "Authorization headers not scanned", "Authorization field not a credential", "auth placeholders flagged". |
| 2 | high | Embedded Kubernetes private keys survive snapshot sanitization | **Fixed by decoding:** every base64 run of 24+ characters (wrapped lines joined) is decoded once, checked as a DER private key and scanned as text with every credential pattern (PEM private keys, tokens, credential URLs, `user:password`, Authorization). So a key or token is found inside base64 wherever it is: kubeconfig `client-key-data`, Secret `data`, any field. `*-key-data` fields are also credential fields, so an opaque literal there is refused too. Public certificate data stays. **Tests:** refusals for a generated Ed25519 key PEM-encoded in `client-key-data`, the same key as base64 DER under an unrelated name, a base64 credential URL in a Secret, an opaque `client-key-data` literal and a bare base64 `user:password` constant; the inert snapshot keeps a kubeconfig with base64 public key data and an exec helper. **Mutations:** "base64 runs not decoded", "decoded base64 not checked for DER keys", "key data fields not credentials"; "base64 user:password not detected" now has a case of its own. |
