**Strongest case against the change, written before deciding**

The suite's execution machinery is part of its evidence boundary. Globally replacing process APIs can make production code under test run a different executable or environment. The PATH-only cache cannot account for the child working directory or later filesystem changes, and one clean-environment sample cannot establish equivalence for caller-supplied SDK variables. A passing suite can therefore cease to describe native behavior.

The new decision-command helpers also perform error handling on behalf of the code they test. Their arbitrary-exception catch manufactures status 1 and stderr without a stack. Consequently, the existing “no stack trace” assertion can pass after the production error formatter is deleted. The redirect tests themselves can silently skip if discovery breaks; their version-output checks do not distinguish wrapped from unwrapped process APIs. Raised timing limits lack measured justification in the allowed evidence. Successful ordinary checks cannot resolve these concerns. **Findings**

1. **F1 — High: preserve real error-handling observability.** In [decisions-why.test.ts](../repo/tests/unit/decisions-why.test.ts:30), arbitrary exceptions are converted to `status = 1; stderr += String(error)`. [decisions-decide.test.ts](../repo/tests/unit/decisions-decide.test.ts:57) uses the same adapter. That is not equivalent to observing a subprocess's stderr. I independently requested the identical fault on fresh base and head clones under Node 24: replace `command.error(error instanceof Error ? error.message : String(error));` in production `decisions/why.ts` with `throw error;`. Both intact controls pass all six tests. Base then fails the explicit assertion excluding `at parseRegister`; head still passes all six. See E10 lines 19–35, 44–93 and E11 lines 19–53. This is a concrete V5/V6 regression even though the assertion text remains. Keep a real command-boundary test for this behavior, and do not normalize unexpected exceptions into expected CLI errors.

2. **F2 — High: the Git wrapper is not behavior-preserving.** [use-real-git.ts](../repo/tests/setup/use-real-git.ts:22) checks relative PATH entries against the parent cwd and caches by PATH alone; the child's `cwd` is not represented. A child with `PATH=bin:/usr/bin:/bin` and its own executable `bin/git` runs that executable natively, but the wrapper substitutes Apple Git. E2 line 5 demonstrates the mismatch; my randomly selected exact-command fresh-clone rerun repeats it at E9 line 5 and exits 1 at line 20. E2 line 6 also demonstrates stale selection after an executable appears earlier on an unchanged PATH. Separately, line 59 injects defaults only for absent variables: the native shim augments caller CPATH and LIBRARY_PATH and prepends MANPATH, while the wrapper leaves the caller values alone (E7 lines 5–7). The new CPATH assertion at redirect-test line 59 endorses this difference instead of comparing native behavior. The config installs this wrapper across all test files and scanner workers. Guard or remove the transformation where equivalence has not been established, and compare actual native behavior in the tests. This finding concerns test fidelity; the targeted hooks/fsmonitor controls still fail as expected, so I do not claim a demonstrated bypass of those production guards.

3. **F3 — Medium: new redirect coverage can pass with missing implementation.** [real-git-redirect.test.ts](../repo/tests/unit/real-git-redirect.test.ts:26) gates all five tests on discovery's own output. Forcing discovery to return an empty string skips all five and exits 0 (E3 lines 255–270). At line 62, the “every way” test checks version text accepted from either executable. Removing only the `execFile` wrapper, or only `spawnSync`, leaves all five tests passing (E3 lines 219–254). Test discovery with controlled inputs and check actual interception/environment behavior per API, including callback and promisified forms. Existing positive controls for other branches do not close this gap.

4. **F4 — Medium: increased timing limits lack measured justification.** [broker-server.test.ts](../repo/tests/unit/broker-server.test.ts:87) raises readiness 5→30 seconds and whole-test timeout 15→90 seconds; [lanes-process.test.ts](../repo/tests/unit/lanes-process.test.ts:12) raises polling 3→20 seconds.
