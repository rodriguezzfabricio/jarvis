# Jarvis: red-team review

October 23, 2026 · Codex · Read-only review; existing files unchanged

## 1. Verdict

Build a narrow pilot; do not implement all 36 decisions as v1. The biggest risk is false confidence: Jarvis can satisfy checks derived from its own mistaken interpretation and report a finished product that Fabricio never wanted. Research before intake and independent verification are the strongest parts. The proposed safety boundary, recovery protocol, and evaluation suite need concrete contracts before unattended runs can justify the promised trust.

**References and verification.** D means [01-decisions.md](/Users/fabriciorodriguez/Desktop/jarvis/docs/01-decisions.md); G means [02-golden-tasks.md](/Users/fabriciorodriguez/Desktop/jarvis/docs/02-golden-tasks.md). Architectural failure scenarios are inferences, not demonstrated exploits. No Jarvis implementation or overnight run was tested.

## 2. Ranked findings

**C1 — Critical: the hard-stop boundary is incomplete.** Where: D12–13, D20–21, D36. Gated commands do not ensure every action uses them. An allowed deploy host can expose destructive operations; a credential wrapper can authorize an unwanted request without revealing its secret. A check after a session cannot undo a send. Verified: [Claude’s sandbox documentation](https://code.claude.com/docs/en/sandboxing) explicitly puts file/web tools, MCP servers, and hooks outside the shell sandbox. Local `codex exec --help` says bypassing hook trust assumes automation has already vetted hook sources; owning a repository is insufficient. **Fix:** enumerate every action channel; keep policy, credentials, and approvals outside writable project files; authorize exact operations and payloads through a broker. Test denial through shell, MCP, browser, and generated application code. Until then, unattended builds get disposable data and no live mutation credentials.

**H1 — High: the benchmark’s expected product violates the existing product scope.** Where: D5, D9, D33, D35; G1–2; [research/06 §5](/Users/fabriciorodriguez/Desktop/jarvis/docs/research/06-product-intake.md). The expected answer includes follow-ups and reply/bounce handling. FreeHire’s actual [delivery backlog, P4.3 and the paragraph after P4.5](</Users/fabriciorodriguez/Documents/ChatGPT/OpenSouce Job/.depth-engine/runs/de-0001/output/delivery-backlog.md:47>) explicitly excludes follow-up campaigns. The research also says to ask before spending *above $10/month*, conflicting with D12’s any-spend stop. Fabricio could receive scope expansion rewarded as correct product thinking. **Fix:** make existing accepted constraints precede generic defaults; grade whether Jarvis discovers and respects them. Correct the benchmark oracle before building intake.

**H2 — High: one intake cannot govern changing requirements.** Where: D4, D7–11. The 15-minute default policy was accepted; the defect is not missing consent to that policy. It is that no procedure handles a discovered infeasibility, a later correction, or a veto after dependent code exists. D7 asks about user-visible choices while D11 puts layout/auth choices in a retrospective Taste report; D4 freezes feature definitions. **Fix:** distinguish delegated preferences from fixed constraints. Version specs, record dependencies, invalidate affected checks, and replan the affected slice. Add an interrupt/feedback inbox and a blocked state for choices outside the grant. The [CLARITI abstract](https://arxiv.org/abs/2604.14624) concerns simulated-user clarification; the [timing study](https://arxiv.org/abs/2605.07937) distinguishes information types. Neither establishes that all new information can safely become a default forever.

**H3 — High: fresh sessions and files do not define crash-safe execution.** Where: D2–4, D14, D26; G10. A process can crash after an external operation succeeds but before recording it. Retrying may duplicate it; not retrying may strand the task. The documents do not specify state authority, atomic transitions, concurrent writers, child-process cleanup, or budget reservations. Stopping new tasks at the cap also leaves in-flight paid calls unresolved. **Fix:** one authoritative ledger with task/attempt IDs, leases, atomic checkpoints, operation receipts, reconciliation, and an explicit unknown-outcome state. Reserve budget before dispatch, include reviewers/tools, specify allowable overshoot, and never silently fall back to paid credentials. Test process death, rate limits, laptop sleep, and ambiguous results; the two-repair rule should not consume its budget on infrastructure outages.

**H4 — High: “outside the model” does not make the evidence independent.** Where: D9, D15–17. A builder can leave tests untouched but change test discovery, scripts, fixtures, or the gate implementation. A screenshot is not proof that an interaction works. A reviewer restricted to the diff cannot inspect an unchanged caller that makes the change wrong. A self-reported confidence of 79 versus 80 is not a calibrated safety threshold. **Fix:** protect the evaluator and acceptance checks outside the build workspace, run them on an immutable candidate revision, and bind evidence to that revision. Permit read-only repository inspection and reproductions. Allow legitimate test changes through separate review. Route uncertain high-impact findings to investigation instead of silently dropping them. [Anthropic’s evaluation guidance](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) explicitly describes model graders as nondeterministic and requiring human calibration.

**H5 — High: shipping ends before proving the deployed service works.** Where: [00-brief.md, Scope](/Users/fabriciorodriguez/Desktop/jarvis/docs/00-brief.md), D12, D16, D30, D33–34; G’s no-deploy policy. Production deployment is appropriately gated, but the plan does not define an authorized release target or distinguish preview-ready from deployed. Monitoring is postponed; migration rehearsal, backup restoration, rollback compatibility, secret rotation, and post-deploy smoke checks are absent from completion requirements. Fabricio can wake to a successful build and a broken live app. **Fix:** define preview-ready, release-ready, and deployed states. Require an environment-specific release manifest, scoped authorization, migration/restore rehearsal, live smoke checks, and an actionable failure signal. Full incident automation can wait; recovery instructions cannot.

**H6 — High: the evaluation fixtures can expose their own answers.** Where: D15, D35–36; G’s “How every task runs” and tasks 3–5. D15 seals history, but G uses linked worktrees at old commits. [Git documents](https://git-scm.com/docs/git-worktree) that worktrees share repository data. I verified the named fixes exist with `git show`; a fresh checkout alone does not hide them. G also permits documentation/package access while D15 says no network, and G1 demands live pricing. **Fix:** export sanitized snapshots into independent repositories with no answer-bearing history, sibling access, or global memory. Keep hidden tests outside them. Separate recorded research fixtures from live-source freshness checks. State which policy governs each phase.

**H7 — High: generated configuration is being asked to prove runtime portability.** Where: D3, D12–13, D20–24, D36; [research/04](/Users/fabriciorodriguez/Desktop/jarvis/docs/research/04-harness-portability-dsh.md). Shared gate commands cannot establish identical permission, desktop, model-routing, or credential behavior. macOS Keychain is not an any-OS credential design. Verified locally: Claude Code **2.1.270**, below D22’s **2.1.302** minimum; Codex **0.163.0**; DSH **0.2.0-rc.2**. [DSH’s README](https://github.com/deepseek-ai/deepseek-harness) confirms its breaking-change preview status. **Fix:** a preflight capability probe and an exact tested version matrix, including desktop launch paths and clean installs. Unsupported combinations must report reduced support or refuse unattended operation. Fall back to one verified CLI adapter; “2.1.302 or newer” is a range, not a reproducibility pin.

**M1 — Medium: the design outline measures consistency more than usability.** Where: D6, D16, D18, D33; G6/G9; [review-prompt.md, pending design outline](/Users/fabriciorodriguez/Desktop/jarvis/docs/review-prompt.md). Different palettes and an AI-tells checklist cannot establish a good workflow. A two-tap approval target may hide the recipient, evidence, or changed message that makes approval meaningful. **Fix:** make directions differ in task flow and information hierarchy; test realistic empty, loading, failure, stale-data, and keyboard states. Measure successful informed completion and misclicks. Preserve domain conventions even when visually ordinary; allow reviewed token exceptions. A morning veto must feed the revision mechanism in H2.

**M2 — Medium: web screenshots cannot certify the promised native products.** Where: D16, D18, D33–34; G9. The only mobile acceptance path uses Expo web. Native login callbacks, permissions, notifications, offline recovery, and installation remain untested; Windows desktop has no corresponding task. Verified: [Expo’s E2E guide](https://docs.expo.dev/eas/workflows/examples/e2e-tests/) tests built APK/app artifacts on emulators/simulators. Also, [Tauri updater signatures](https://v2.tauri.app/plugin/updater/) and [macOS signing/notarization](https://v2.tauri.app/distribute/sign/macos/) are separate mechanisms; free updater signing does not remove distribution friction. **Fix:** certify each target through a built artifact and native smoke flow, or explicitly call the first release web-only. D34 already acknowledges signing costs; carry that limitation into the delivery promise.

**M3 — Medium: v1 is a platform before it proves an advantage.** Where: D1–3, D24, D27–31, D35–36. Fourteen skills, three adapters, routing, sweeps, and ablations create maintenance before demonstrating that intake improves Fabricio’s results. Ten tasks twice across three harnesses means at least **60 full attempts per complete evaluation cycle**, before variants. D24 always routes planning/review to strong high-effort models and assigns test execution to models, contrary to the supplied difficulty-based routing rule. **Fix:** deterministic execution first, cheapest capable model by task, escalation on observed failure, one writer/browser initially. Measure peak RAM/disk and cost per accepted result; small Markdown memory does not measure the footprint of browsers, builds, and worktrees.

## 3. End-to-end scenario: recruiter finder overnight

1. **Research:** Jarvis reads FreeHire, then consults its expected answer. **Break H1:** it adopts follow-ups despite the accepted backlog. A polished spec now encodes the wrong product.
2. **Intake:** Fabricio leaves; delegated defaults apply. A provider proves unavailable. **Break H2:** there is no explicit rule for preserving the goal while replacing that dependency and invalidating the old checks.
3. **Build:** contact → draft → approval → local SMTP works. **Break H4:** permissive fixtures and a diff-only reviewer can miss an integration defect; green checks validate the stubbed path.
4. **Interruption:** after a separately authorized live send, the process loses the response. **Break H3:** replay must reconcile the unknown outcome, not send again. FreeHire’s P4.5 already requires this; Jarvis needs equivalent discipline for its own operations.
5. **Morning:** tests and screenshots pass. **Break H5:** without target authorization it is release-ready, not deployed; with authorization it still needs deployment evidence and recovery checks. The report must state the actual achieved state.

## 4. Cut list and smallest useful first version

1. **Postpone** Codex/DSH parity, desktop integrations, and Windows packaging until one CLI adapter passes safety and restart tests.
2. **Postpone** parallel builders, workflow-API cloning, automated memory promotion, weekly sweeps, and per-model scaffolding ablations.
3. **Postpone** native-app templates and broad stack curation. Use FreeHire’s stack plus one small greenfield web fixture.
4. **Keep** research/intake, a versioned task contract, one bounded worker, protected checks, a fresh reviewer, and a report with revision-linked evidence.
5. **Prove** one thin recruiter path against stubs, one unseen small web app, and one killed-and-resumed run. For the web fixture, use a disposable preview only within an explicit deployment grant. Compare against the same native harness without Jarvis.

This is a **3–5 engineering-day pilot target**, conditional on usable local environments; it is not an estimate for the full promise. Success means fewer wrong assumptions and corrections at a stated cost, not merely more workflow artifacts. Basis: D1, D3, D16, D35–36.

## 5. Test-plan gaps

1. **Independent outcome oracle:** G1–2/D35 must accept valid alternatives and preserve actual constraints. Historical fixes are examples, not proof of security: in `971efc2`, `TestLLMDrafterDelimitsUntrustedFields` uses a fake generator and asserts prompt strings. I inspected that diff; it does not test a model resisting injection. Add malicious-content trials and verify action confinement, with no claim of universal injection immunity.
2. **Isolation and reproducibility:** G/D15 need the sanitized snapshots from H6, baseline failures and known-good passes, pinned fixtures/dependencies, and fresh memory for every run. Validate that the original buggy version fails the hidden checks.
3. **Coverage:** G9–10/D16/D35 need an unrelated greenfield app, changing requirements, migration/restore, native builds, clean-machine installation, expired credentials, and actual release recovery. Ten variations around FreeHire cannot support “build anything.”
4. **Runtime fault injection:** G10/D3/D12–14 must kill the runner at state transitions, exhaust budgets mid-request, disable hooks, present hostile tools/pages, and tamper with evaluator inputs. Check that safety blocks succeed independently of model cooperation.
5. **Measurement:** D22/D26/D35 need an equal-budget native-harness baseline, held-out tasks, repeated reliability, false-DONE rate, blocked-but-correct rate, actual user corrections, and cost per accepted outcome. Two repeats are a starting smoke test, not parity evidence. Calibrate the UX/product grader with Fabricio; do not label guessed interventions as observed ones.

## 6. Strongest alternative

**Build a portable acceptance package, not a portable orchestrator.** Keep requirements, task contracts, protected acceptance tests, and evidence portable. Let each native harness manage sessions and coding; use one pinned community workflow on the primary harness, with narrowly scoped automation and CI verification. [Compound Engineering’s README](https://github.com/EveryInc/compound-engineering-plugin) documents a hands-off build/review/browser-test/CI loop, making it a real baseline against D1/D31/D36. Its default push/PR behavior needs explicit scope and containment; it is not the missing security boundary.

This likely beats Jarvis on shipping speed and maintenance for Fabricio’s first projects. It loses uniform orchestration, cross-harness resume, and centralized routing. Jarvis earns a custom runner only if controlled comparisons show those losses cause recurring failures worth the maintenance. Native capability differences should be explicit rather than hidden behind generated files.

## 7. Three changes first

1. **Repair the oracle:** reconcile the recruiter expectations with FreeHire’s accepted scope and money policy; isolate the fixtures; establish a native-harness baseline.
2. **Specify the trust and recovery contracts:** enumerate action channels, approval scope, protected checks, durable transitions, budget handling, and unknown outcomes before writing the runner.
3. **Ship one measured slice:** one CLI, one worker, versioned intake, protected verification, and a truthful morning report; expand only after it beats the baseline.
